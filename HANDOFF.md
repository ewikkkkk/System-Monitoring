## 1. Which database, and which schema/tables does it read and write?
Production database name is not supplied yet. Use the METS Hub application database; apply numbered migrations 001–008 in order with a migration ledger owned by the host. Schema: monitoring. Reads People, Tasks, TaskHistory, Deployments, Vouchers, VoucherHistory; inserts/updates Tasks and Vouchers; inserts TaskHistory, Deployments and VoucherHistory. Migration 005 adds the production event log; 006 and 007 add voucher inventory and history; 008 adds nullable JSON attempt details to VoucherHistory. SQL Server 2016+ with database compatibility level 130+ is required for OPENJSON/ISJSON. People must be provisioned from the host directory by an operator. SQL mode inserts no sample people, tickets or vouchers. Explicit local demo mode uses `.local/monitoring-demo.json` (people/tasks/history/deployments/vouchers/voucherHistory collections), a file-backed JSON database; no SQL tables are touched in demo mode. Voucher collections are initialized lazily without replacing existing demo data.

Real SQL Server target and credentials are not provided. Migrations have not been applied. SQL Server acceptance is not passed. Explicit `npm run demo` uses a local JSON file database, four fictional people, six sample tasks, and a fixed server-supplied demo identity. Voucher monitoring accepts manual codes or text-based UniFi voucher PDFs with a required Bancal 1/Bancal 2 inventory tag. Location-mismatch attempts remain Active and preserve findings plus ticket/recipient/device/purpose/time context in history, so the code can be used at its tagged location later. Matching successful use becomes Used; matching manual invalidation becomes Invalid. Duplicate imports skip existing records without modifying them. SQL uses transactions/locks; demo uses serialized file updates. Source PDFs are not uploaded or retained. PDF.js 5.6.205 is the one new browser dependency; include its Vite-emitted worker asset when integrating. Node 20.19+ is required. No new environment variables. Migration 008 and real SQL Server acceptance remain unverified. No automatic METS One to-do sync exists; integration still needs host assignment/user mapping and Help Desk/METS One APIs.

## 5. Which routes must be restricted, and to whom?
All /api/system-monitoring routes require authenticated monitoring-team access at router level. GET /tasks, GET /people, GET /tasks/:id/history, GET /deployments: authorized monitoring viewers. POST /tasks, PUT /tasks/:id, PATCH /tasks/:id/status: developers, testers, and team leads. POST /deployments (Deployment/Fix/Revert): release managers and team leads. Apply method-level policy in host router middleware. No client identity or local authorization tables are accepted.

GET /vouchers, GET /vouchers/:id/history, POST /vouchers, POST /vouchers/import, POST /vouchers/:id/use and POST /vouchers/:id/restore: authorized Infra staff and Infra team leads only. Voucher codes may grant network access; general task viewers must not inherit access to these endpoints. The host owns all router-level authorization. Process engineer task access must also be granted by the host according to company policy.
