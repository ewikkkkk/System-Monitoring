## 1. Which database, and which schema/tables does it read and write?
Production database name is not supplied yet. Use the METS Hub application database; apply numbered migrations 001–011 in order with a migration ledger owned by the host. Schema: monitoring. Reads People, Tasks, TaskHistory, Deployments, Vouchers, VoucherHistory, BugOccurrences; inserts/updates Tasks and Vouchers; inserts TaskHistory, Deployments, VoucherHistory and BugOccurrences. Migration 005 adds the production event log; 006 and 007 add voucher inventory and history; 008 adds nullable JSON attempt details to VoucherHistory; 009 adds Tasks.relatedTickets; 010 adds BugOccurrences; 011 adds Tasks.moduleName without remapping existing system values. SQL Server 2016+ with database compatibility level 130+ is required for OPENJSON/ISJSON. People must be provisioned from the host directory by an operator. SQL mode inserts no sample people, tickets or vouchers. Explicit local demo mode uses `.local/monitoring-demo.json` (people/tasks/history/deployments/vouchers/voucherHistory/bugOccurrences collections), a file-backed JSON database; no SQL tables are touched in demo mode. Voucher collections are initialized lazily without replacing existing demo data.

## 4. What is unfinished, stubbed, or returning a fake number? Be blunt.
Real SQL Server target and credentials are not provided. Migrations have not been applied. SQL Server acceptance is not passed. Explicit `npm run demo` uses a local JSON file database, four fictional people, six sample tasks, and a fixed server-supplied demo identity. Demo counts are computed from saved demo records; they are not production metrics. This adapter is throwaway development code, not SQL emulation or a multi-process database. Demo data is not transferred to SQL. People synchronization must be supplied by the hub; there is no directory-management UI. IT Help Desk integration is not wired: reference is stored as external ticket text until the host supplies the Help Desk URL/API and mapping. Task numbers are derived from the existing numeric task ID with BUG/ENH prefixes; no new SQL column or migration is needed. Include shared/task-number.js in the integration. No task imports, attachments, notifications, deletion, or AI features. Related-ticket links use the existing Help Desk placeholder; they do not validate or fetch Help Desk tickets. History records status/notes and acting user on each save, not every field-level diff. Concurrent edits use last-write-wins. SQL local developer identity requires DEV_USER_ID; production identity must come from the host. Build/start checks are tracked in README.

The user explicitly requested a module sidebar after the original no-sidebar constraint. Its component is isolated in ModuleSidebar.jsx so the hub can reuse or replace it. Overview, List, and Calendar are available; Table was removed and card layouts were replaced by flat rows/sections. The entry heading and summary strip were subsequently removed. Overview reports derive solely from the current filtered task records, not historical status snapshots; completion time uses valid creation/completion dates, and estimated effort is not tracked time. The requested theme switch uses the host darkMode/onToggleDarkMode contract; only the local preview persists its theme in browser storage. Per-task detail is a separate view, and creation/editing uses a floating modal. Calendar requires migration 005. Deployment/fix/revert records are append-only reference logs; no real deployment or rollback is executed and logging does not change task status. Revert must link to an unreverted deployment/fix for the same task and have an event time at or after that original event. Dates are stored as UTC and displayed in browser local time. SQL validation and SQL migration execution remain unverified because no real database target is configured.

Calendar daily reports are generated locally from saved production events, with copy-to-clipboard and manual-copy fallback; no AI service or additional SQL tables are involved. Demo reports explicitly identify sample records. List displays pending concerns as flat rows without status-group collapse controls. External ticket references have a separate List column and open a new-tab local placeholder with the ticket number. The actual IT Help Desk connection is still unconfigured; the query placeholder does not fetch Help Desk or SQL records. Its resolver lives in src/services/api.js.

Voucher monitoring accepts manual codes or text-based UniFi voucher PDFs with a required Bancal 1/Bancal 2 inventory tag. Location-mismatch attempts remain Active and preserve findings plus ticket/recipient/device/purpose/time context in history, so the code can be used at its tagged location later. Matching successful use becomes Used; matching manual invalidation becomes Invalid. Existing Invalid records with an explicit location-mismatch finding may be returned to Active with an operator reason; Used and unrelated Invalid records cannot be restored. Duplicate imports skip existing records without modifying them. SQL uses transactions/locks; demo uses serialized file updates. Network provisioning, code validation against equipment, ticket existence checks, expiry, general reactivation and approvals are not implemented. Import reads PDFs in the browser (10 MB / 30 pages / 500 codes maximum), preserves leading zeros, and allows reviewing/unchecking codes. Colored markings, printed speed/data/validity limits and scanned-image PDFs are not interpreted. Operators must review availability; importing does not validate network usability. Source PDFs are not uploaded or retained. PDF.js 5.6.205 is the one new browser dependency; include its Vite-emitted worker asset when integrating. Node 20.19+ is required. No new environment variables. Migration 008 and real SQL Server acceptance remain unverified. No automatic METS One to-do sync exists; integration still needs host assignment/user mapping and Help Desk/METS One APIs.

List defaults to unfinished concerns; selecting Prod live or Closed shows those completed records, with matching headings and Overview status drill-down. Bug activity uses task creation timestamps for new bugs plus append-only, explicitly reported BugOccurrences for recurrences. Status edits, related-ticket links and deployments do not silently generate bug reports. Counts are scoped to currently filtered tasks and their current system/type classification. Local-day buckets preserve zero-report days; future/invalid timestamps are excluded. Seven-day before/after comparisons use exact release timestamps and only the same system, with the after window marked incomplete until 168 hours elapse. A timestamp correlation is not deployment causality. Prior recurrence history is not inferred or backfilled; historical reopen cycles are not reconstructed. Explicit recurrence reports may reopen a completed bug and preserve earlier task history, ticket reference, notes, actor and optional production event. Recurrence dates cannot precede task creation or a linked event, or be in the future beyond a one-minute clock allowance. No new dependencies or environment variables for this change. Migrations 009/010 and real SQL Server recurrence acceptance are unverified. Demo tests use actual persisted file records, not SQL Server.

Task creation has explicit Bug/Enhancement choices and requires one of WMS, Client Portal, RF Barcoding, PISA, CMMS or TOLL as System. Module is separate text, up to 120 characters. Existing nonstandard/empty system values are preserved unchanged on edit until an operator explicitly selects a canonical value; they are not silently inferred or moved to Module. Old clients that omit moduleName preserve its stored value. Daily resolutions derive from TaskHistory transitions into Prod live/Closed, not repeated completed edits or Prod live-to-Closed changes. Resolutions survive later reopening and are deduplicated per task per local day; a task resolved again on a later day is counted on that day too. Tasks lacking resolution history may use their saved completedAt timestamp, never an invented date. Pending bug/enhancement totals use current unfinished statuses across all dates in the current task/system filters. Migration 011 and real SQL Server acceptance remain unverified. No dependency or environment variable additions.

## 5. Which routes must be restricted, and to whom?
All /api/system-monitoring routes require authenticated monitoring-team access at router level. GET /tasks, GET /people, GET /tasks/:id/history, GET /deployments, GET /bug-occurrences, GET /task-resolutions: authorized monitoring viewers. POST /tasks, PUT /tasks/:id, PATCH /tasks/:id/status, POST /tasks/:id/occurrences: developers, testers, and team leads. POST /deployments (Deployment/Fix/Revert): release managers and team leads. Apply method-level policy in host router middleware. No client identity or local authorization tables are accepted.

GET /vouchers, GET /vouchers/:id/history, POST /vouchers, POST /vouchers/import, POST /vouchers/:id/use and POST /vouchers/:id/restore: authorized Infra staff and Infra team leads only. Voucher codes may grant network access; general task viewers must not inherit access to these endpoints. The host owns all router-level authorization. Process engineer task access must also be granted by the host according to company policy.
